### 2026-09-30 — `review_on` 문서 발견 범위

- 저장소: `mogi-productivity`
- PR: #7 `Warn when implementation docs need review`
- 모기의 질문: “validator가 frontmatter를 저장소 전체에서 찾는 것은 아니다”는 문장은, 전체 탐색이 일반적인데 이 구현은 그렇게 하지 않았다는 뜻인가?
- 확인한 답: 일반적인 방식을 평가하는 문장이 아니라 구현 범위를 밝히는 문장이다. 검사 대상 문서는 `REVIEW_DOCUMENTS`의 두 파일로 고정되고, 각 문서의 `review_on`은 그 문서를 언제 검토할지만 선언한다. 다른 문서에 `review_on`만 추가해도 자동으로 발견되지는 않는다. 왜 고정 목록 방식을 택했는지는 저장소 근거에서 확인할 수 없다.
- 관찰: “범위는 선언적이지만 문서 발견은 고정 목록”이라는 표현만으로는 이 문장이 관례 비교가 아니라 오해 방지용 구현 경계 설명이라는 점이 바로 드러나지 않았다.
- 후속 메모: 에이전트가 새 문서에 `review_on`만 추가하면 자동으로 검사 대상이 된다고 구현 중 착각할 여지가 있다. `REVIEW_DOCUMENTS` 근처에서 고정 등록이 필요하다는 사실을 작업 중 발견할 수 있게 하는 주석은 개선 후보지만, 아직 제안일 뿐이며 대상 저장소에는 반영하지 않는다.

### 2026-09-30 — CALL TREE의 의미

- 저장소: `mogi-productivity`
- PR: #7 `Warn when implementation docs need review`
- 모기의 질문: Whiteboard의 `완료 검사 경로 — 이전과 이후` CALL TREE는 무엇을 나타내는가?
- 확인한 답: 실제 실행에서 자동 수집한 trace가 아니라, PR 전후의 코드 경로를 설명하기 위해 작성된 `call_stack_diff`다. 이전에는 package command 진입점이 없었고, 이후에는 `pnpm validate:docs-impact` → `runDocsImpactValidation` → `getDocsImpact` → frontmatter 파싱·glob 매칭 순으로 이어짐을 보여준다. 오른쪽 `+N -N`은 호출 횟수가 아니라 연결된 코드 범위의 diff 증감이다.
- 관찰: `CALL TREE`와 `이전과 이후`만으로는 실제 실행 trace인지, 작성자가 구성한 코드 안내 경로인지 바로 구분되지 않았다.
- 후속 관찰: 모기는 호출 경로 자체는 이해했지만, 각 행의 `인자·출력·exit code 경계`, `refs`, `문서별 warning 수집`, `제한된 review_on 계약`, `segment glob`, `package command surface` 같은 설명이 압축적이고 추상적이라 무슨 동작인지 이해하기 어렵고 마음에 들지 않았다. 함수 옆 설명은 내부 용어보다 “이 단계에서 실제로 무엇을 하는가”를 평문으로 써야 한다.
- 반영: Whiteboard 리뷰 version 25에서 CALL TREE 제목과 각 행을 평문으로 교체했다. 트리 구조와 실제 코드 링크는 유지했다.

### 2026-09-30 — 삭제·이름 변경 경로를 확인하는 방법

- 저장소: `mogi-productivity`
- PR: #7 `Warn when implementation docs need review`
- 질문 요지: 테스트 설명을 읽다가 삭제한 파일과 이름 변경 전후 경로를 어떻게 확인하는지, 파일 식별키가 있는지 궁금해했다.
- 확인한 답: `getDocsImpact`는 `git diff --name-status -z --find-renames`로 비교 시작점과 head의 변경 목록을 얻는다. 삭제는 이전 경로가 출력되고, Git이 이름 변경으로 판단한 항목은 이전·이후 경로가 함께 출력된다. `parseNameStatus`는 이름 변경 항목의 두 경로를 모두 읽고, `changedPaths`에 모아 문서의 `review_on`과 대조한다. Git의 이름 변경 판정은 파일의 영구 식별키가 아니라 내용의 동일성·유사성을 바탕으로 한다. 이름 변경으로 인식되지 않고 삭제·추가로 나오더라도 이 구현은 두 경로를 모두 수집한다.
- 테스트 근거: `scripts/test/docs-impact.test.js`의 삭제·이름 변경 테스트는 구현 파일 삭제, 구현 폴더 밖으로 이동, 구현 폴더 안으로 이동을 만들고 각각 삭제 경로·이동 전 경로·이동 후 경로가 경고에 포함되는지 확인한다.
- 관찰: 모기는 현재 version 26의 테스트 섹션을 읽는 중이며, 이 질문은 개발자로서의 흥미라고 밝혔다. 설명 수정 요청이나 이해도 평가는 아직 없다.

## 이해에 도움된 부분

- CALL TREE의 함수 호출 구조는 유지하되 각 행을 내부 용어가 아닌 “이 단계에서 실제로 무엇을 하는가”라는 평문으로 바꾸자 모기가 수정된 설명에 매우 만족했다. 이 사례에서는 다이어그램 종류보다 행 라벨의 언어가 이해도에 직접 영향을 주었다.

## 여전히 설명되지 않은 부분

- 원문 코드로 이동하는 링크는 좋지만, 전체 코드가 나타나면 실제로 읽지 않게 된다는 관찰이 나왔다. 필요한 코드 범위와 그 코드의 의미를 함께 보여주는 표현이 필요하다는 사용자 선호를 확인했다.
- 특정 구현 내용 중 무엇이 여전히 이해되지 않았는지는 별도로 확인하지 않았다.

## Cubic 부분의 이해 어려움

모기가 Cubic 리뷰의 앞 두 항목을 이해하지 못했다고 명시했고, 여기서 파일과 일반 대화 세션이 무엇인지 다시 물었다. 모기는 P1·P2라고 지칭했지만 현재 version 59를 다시 읽어 데이터 관련 앞 두 지적이 모두 P2임을 확인했다. 번호 정정 자체보다 개념 설명이 필요하다.

`todo/chats/README.md`와 archive 생성 코드를 다시 읽어, 세션은 모기와 투두냥의 Codex 대화 한 묶음이고 SessionEnd 때 대화 원문이 Markdown 파일로 저장되는 것을 확인했다. 일반 완료 세션은 루틴 명령만 수행한 자동화와 진행 중 대화를 제외하고 누적 검토 대상으로 세려는 대화이며, 할 일 전부가 완료됐다는 뜻이 아니다. 웹 쇼핑·재활 대화의 세대와도 구분한다.

첫 지적은 archive 파일을 만드는 쪽이 허용하는 ID 문자와 검토 노트에서 파일명의 ID를 읽는 쪽의 허용 문자가 달라 일부 유효한 대상 파일을 알아보지 못하는 문제다. 가상 파일명 `...--AB12xy34.md`로 생산자·소비자의 검증 규칙 차이를 설명한다. 두 번째는 자동화 세션을 특정 첫 요청 문구가 들어간 파일명과 사용자 턴 수로 제외해서, 같은 루틴 실행도 문구·턴 수가 달라지면 일반 대화 수에 들어갈 수 있는 문제다. 일반 작업 대화와 정기 명령 실행의 예시로 구분해 설명한다.

Cubic을 포함했다는 사실만으로 모기가 지적을 이해했다고 해석하지 않는다. 사례는 설명용이며 개인 파일·현재 실제 count를 새로 확인한 것이 아니다. 이 질문은 관찰 일지에 기록했고 Cubic 전달 목록을 MAILBOX에 다시 추가하지 않았다. 이번 Whiteboard 문서 편집이나 원본 구현 수정은 하지 않았다.

## Whiteboard에 대한 불편과 레거시 입력을 다루는 관점

모기는 이번 PR Whiteboard에 거슬리는 점이 있다고 평가했다. 잘못된 레거시 데이터가 남아 있다면 그 데이터까지 포함해 테스트가 깨지지 않도록 분기를 보강하기보다, 오염된 레거시 입력을 없애는 방향이 맞다고 생각한다고 말했다. 이는 단순히 함수·용어를 이해하지 못했다는 피드백이 아니라 설명과 검토의 전제에 대한 비판이다.

화이트보드냥이는 이번 루틴 사례에서는 동의했다. 기존 설명은 Cubic의 지적이 현행 코드에서 재현되는지를 확인하는 데 치우쳐, 현재 제품·운영에서 해당 입력을 유지할 필요가 있는지를 먼저 따지지 못했다. 가상 반례 재현은 조건의 취약성을 확인하지만 그 조건을 더 정교하게 유지해야 한다는 결론까지 증명하지 않는다. 현재 launchd는 새 Codex 세션을 생성하지 않으므로, 예전 루틴 전용 기록을 일반 검토 입력에서 정리하고 전용 분기를 제거하는 방향이 가능하다.

이 방향의 테스트는 폐기할 과거 입력을 계속 지원하는 것이 아니라, 일반 대화 집계가 올바르게 유지되고 정리 후 참조·수집이 깨지지 않는지를 확인하는 데 맞춘다. 단지 오래됐다는 이유만으로 모든 과거 기록을 오염으로 간주하거나 일괄 삭제하는 규칙으로 확대하지 않는다. 실제 판단 기준은 현재 집계 입력으로 필요한 데이터인지다.

이번 피드백은 관찰과 논의로 기록했다. 앞서 전달한 루틴 기록 정리 방향 외에 새 할 일을 MAILBOX에 자동 추가하지 않았다. 원본 코드·테스트·대화 파일이나 Whiteboard 본문도 변경하지 않았다. 설명 만족도나 전체 읽기 완료를 긍정적으로 결론 내리지 않는다.

## P3 테스트 종료 설명의 이해 어려움

모기는 Whiteboard로 돌아와 P3를 이해하지 못했다고 말하고 자신의 기술적 이해가 부족한 것 같다고 표현했다. version 59의 block-63과 고정 head의 `server.test.js:19–48`, `server.js:28–37`, `serve.js:28–31`을 다시 읽었다. 설명에는 테스트가 수집 완료를 일부러 보류한다는 배경과 정상·실패 경로를 먼저 제시할 필요가 있었다. 이 반응을 모기의 전반적인 기술 역량 부족으로 해석하지 않는다.

해당 테스트는 동시 갱신 두 번이 한 수집을 공유하는지 확인하려고 수집 결과를 일부러 미완료 상태로 둔다. 정상 경로에서는 검증 뒤 `complete(...)`를 호출해 요청 두 개가 끝나게 한다. 그 호출 전에 assertion이 실패하면 작업을 풀어주는 코드에 도달하지 못하고, after 정리가 `server.close()`로 열린 HTTP 요청이 끝나기를 기다릴 수 있다. 테스트는 실패했는데 정리까지 끝나지 않아 실행이 멈추는 문제다.

Java·Spring 통합 테스트에 비유해, mock 서비스의 CompletableFuture를 일부러 미완료로 두고 검증하던 중 실패하여 complete를 못 했는데 AfterEach의 서버 종료가 그 요청을 기다리는 흐름으로 설명한다. 비유이며 실제 구현은 Node HTTP 테스트다. 필요한 정리는 실패 경로에서도 보류한 작업과 연결을 종료하는 것이다. 고정 코드의 실제 CLI 종료에는 이미 closeAllConnections가 있고 테스트 정리에는 없다는 차이를 구분한다.

원본 코드나 Whiteboard를 수정하거나 새 테스트를 실행하지 않았다. Cubic P3는 새 MAILBOX 전달로 중복 추가하지 않았다. 설명을 제공한 것과 모기가 이해했다고 확인한 것은 구분한다.

모기는 후속 답변에서 CompletableFuture 비유가 좋다고 명시적으로 평가하고, 타임아웃을 정하지 않은 것이라고 이해했다. Java 비유가 이 P3 설명의 이해에 도움을 줬다는 확인이다. 기다림에 상한이 없다는 지점은 맞으며, 테스트 timeout 설정만으로 미완료 작업과 HTTP 연결 정리가 보장되지는 않는다고 보충한다. 이번 P3의 핵심은 검증 실패 경로에서도 정리가 완료되도록 하는 것이다. 이 확인을 전체 PR 설명 이해나 다른 비유의 효용으로 확대하지 않는다.

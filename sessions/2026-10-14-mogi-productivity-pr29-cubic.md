## Map 제안과 ‘다시 조회’의 의미 구분

모기는ID배열과예약일배열을별도로요청한다는뜻인지확인하고Map을쓰면되는지,왜다시조회하는지물었다. 고정reviewhead d8b3ee9와현재242fa4e의snapshot.js를비교했다. 선택한최대10개의readOpen상세조회는수정전에도이미있었고이번대응에서조회호출을추가하지않았다. 추가된것은기존상세결과의scheduledOn===null을필터링하는단계다.

Map은예약일의주인ID가이미맞게붙은데이터를저장/검색하는데유효하다. 현재예약일배열의값에는그값의ID가없으므로두배열을같은인덱스로짝지어Map에넣어도잘못된짝이그대로남는다. 처음부터ID와예약일을결합해읽는조회방식변경과Map자료형변경은구분한다. 현재ID→listOf Map은이미존재하지만후보속성별배열의짝문제와는별개다.

채팅에서는이전‘다시조회’표현이추가호출처럼읽힐수있음을바로잡아후보조회→추첨→이미필요한10개상세조회→반환된예약일검사라는실제흐름을설명한다. 전체후보를ID별로조회했을때의소요시간이나묶음객체조회지원여부는측정/조사하지않았고단정하지않는다. Map재설계·구현수정·테스트·MAILBOX·통신·Whiteboard·커밋/푸시는없다.

## 설계 비교 — ID와 값 결합을 먼저 보장할지, 현재 상세 검사를 유지할지

모기는현재대응과처음부터Map으로받는설계중무엇이나은지,자신이억지인지물었다. Things공식AppleScript안내·Apple공식문서와설치Things.sdef의id/activation date등읽기속성을확인했다. 공식안내는컬렉션순서가앱화면순서와같다고설명한다. ID별로필요값을읽어한항목레코드로결합하고Map에넣는방향은가능하지만,원하는필드만ID와묶어서빠르게일괄조회하는방식의동작/성능은이번에실기기확인하지않았다. 불가능하다거나반드시17초걸린다고단정하지않는다.

비교는①따로받은배열을인덱스로Map에넣기(짝문제유지),②ID고정/ID와필드를결합해전체후보의값읽기(주인짝은명확,호출비용비교필요),③현재속성별일괄후보조회후선택최대10개상세결과필터(추가조회없이표시대상예약확인,후보단계누락/순서문제자체는잔존)로나눈다. Map구현이틀렸다는식으로설명하지않고조회응답에서ID와필드의주인이결합되는방식을비교한다.

화이트보드냥은모기가명시한빠른임의상기목적에는현재대응을이번PR에서유지하는것이실용적이라고제안하되완전한후보정확성의해결이라고말하지않는다. 먼저ID와예약일을묶는설계는더명확하며전체후보를항목별로읽으면앱호출이늘수있어측정으로비교해야한다. 상세검사로잘못들어온예약항목은제외해도처음잘못제외된예약없는항목은복구하지못한다는한계를알린다. 사용자두번째지적수용·설계변경결정은아직미확정이며MAILBOX자동승격·원본변경·개인앱시험·Whiteboard·통신은없다.

## 현재 대응을 실제 코드로 연결

모기는현재대응을잘이해하지못했다고밝히고코드설명을요청했다. 현재PR29 OPEN·같은242fa4e를재확인한뒤snapshot.js22~35,readOpen,read-open.applescript의정확ID조회/activation date반환과수정diff를읽었다. 현황판갱신→collectSnapshot/readDashboardTodos에서기존후보조회/추첨→listOf(ID→목록)Map의keys를readOpen에전달→정확ID별상세결과todos→scheduledOn===null필터→그결과를반환하는실제흐름으로설명한다. Map의값이예약일이아니라목록명임을구분하고JS keys/spread·filter의실제동작을쉬운말로붙인다.

가상선택ID B치과가예약없는후보로잘못들어왔다면상세조회에서B의현재예약일이반환되어필터에서제외되고,C빨래의예약일null은남는값흐름을연결한다. fixture예시는실제개인항목조회가아니다. 대응추가는이미필요한상세조회뒤필터이며추가AppleScript실행을넣은것이아니다. readOpen최대10개와정확10개보장도구분한다. 코드설명은채팅만수행하고Whiteboard/원본/MAILBOX/통신/시험/커밋푸시는없다. 이번대목이해완료는미확인이다.

## 이해 확인 — 배열 재매칭과 예약일 조건 검사 구분

모기는 코드 설명 뒤 이제 이해했다고 명시했다. 처음에는 검사만으로 ID 배열과 예약일 배열을 다시 매칭할 수 있는지 의문이었지만, 실제 대응은 예약일이 존재하는 항목을 제외하는 조건이라 가능하다고 자신의 말로 설명했다. 이어 이 정도면 될 것 같다고 현재 대응을 수용했다.

이해가 확인된 대상은 **정확한 ID로 이미 읽은 상세 객체의 예약일을 검사해 걸러내는 것과, 처음의 두 배열을 재매칭하는 것은 다른 동작**이라는 점이다. 같은 가상 치과·빨래의 상세 결과를 놓고 scheduledOn===null의 참/거짓과 남는 배열을 코드로 보여준 설명 뒤 이 재진술이 나왔다. 칭찬만으로 추정한 이해가 아니며, 사용자가 밝힌 초기 혼동과 이를 해소한 조건을 기록한다.

이 수용은 현재 두 번째 지적의 대응 범위에 대한 판단이다. 전체 후보의 배열 순서 문제 자체 해결·후보 누락 복구·정확10개 보장·PR전체읽기/검증/머지 완료로 확대하지 않는다. 추가 구현·MAILBOX·투두냥 메시지·Whiteboard·커밋/푸시는 수행하지 않았다.

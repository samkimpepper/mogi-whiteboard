## 설명한 실제 흐름과 경계

기존 ID 명령은 Node에서 서울 시간대/명시적 날짜·시각을 검사하고, AppleScript로 Mac Things의 정확한 ID·허용 Area 또는 프로젝트 Area·수정시각·open 상태를 읽는다. Preview는 토큰/전송 없이 계획을 반환한다. Apply는 JSON을 Swift 프로그램 stdin으로 보내며 Swift가 기존 update 토큰을 전용 Keychain에서 읽는다. 승인 지연 뒤 같은 선택을 다시 읽어 최초 다섯 값 원문과 같을 때만 id/auth-token/when URL을 Mac Things 앱에 전달한다. 다른 필드 변경은 요청하지 않는다.

`requested`는 Mac 앱 실행/전달 완료까지이고 Things 수락·reminder 설정·실제 알림 발생의 확인이 아니다. 기존 reminder/반복 여부를 읽는 경로가 없고 반복 when 수정은 Things 공식 계약이 거부한다. 실패/timeout 때 이미 전달됐을 수 있어 자동 retry·대체 생성은 없다. 마지막 비교 뒤 변경, 출력된 수정시각이 같은 변경, 아직 Mac에 도착하지 않은 폰 변경은 막지 못한다.

시각 add는 허용 Area 직접/프로젝트 항목에서 대소문자까지 같은 제목이 0/1/여럿인지 보고 create/reuse/거부한다. Create에는 토큰이 필요 없으며 새 ID 회신을 받지 않아 ID를 발명하지 않는다. Reuse에는 새 Notes/checklist를 넣지 않는다. 날짜만 add는 기존 별도 경로로서 입력만 preview하고 apply에서 Notes·일정을 갱신한다. 이번 두 후보 수 검사와 일반 오류 메시지 변경도 설명했다.

토큰 등록 때는 clipboard→Node stdin→Swift stdin→Keychain이며 Node도 토큰을 다룬다. 기존 항목 apply는 Swift에서 토큰/URL을 다루고 Node에는 상태만 반환한다. 등록/적용을 구분했다. Presence는 비밀 데이터 자체를 요청하지 않으며 토큰 유효성 확인이 아니다. 개인 token·제목·ID·Notes는 기록하지 않았다.

## ID reminder의 수정 시각 중단 조건 재검토·사용자 선택 전달

모기는 재확인의 다섯 값에 제목/Notes도 포함되는지 물었다. 실제 값은 ID/Area/project/수정시각/open 상태이며 본문 자체 비교는 아니고 수정시각으로 변경을 간접 감지한다고 설명했다. 폰을 그 순간 만지지 않아도 이전 변경이 두 조회 사이 Mac에 동기화돼 비교값을 바꾸면 중단될 수 있고, 동기화 자체를 중단 신호로 쓰는 것은 아니라는 점을 구분했다.

모기는 수정시각 변경만으로 중단하는 것이 너무 엄격하다고 의견을 냈고 정확한 ID에는 요청한 시각을 덮어쓰는 것이 맞다고 선택했다. Notes 변경까지 막는 넓은 검사와 알림 자체 변경을 구별하지 못하는 한계, 허용 Area/열린 상태의 직전 재확인 유지, 명시적 ID와 제목으로 대상 선택의 구분을 논의했다. 모기의 명시적 요청으로 MAILBOX에 수정시각 변화만으로 중단하지 않고 요청값을 적용하는 방향을 추가했다. 제목 선택 검사를 자동 제거하거나 실제 저장값 자동 확인까지 구현된 것으로 확대하지 않았다. 기존 입력/사람 확인 요청도 보존했다.

이는 사용자 선택을 전달한 기록이며 원본/PR 코드 변경·시험 실행·새 보충 신호·Whiteboard 편집은 없다. v32 유지, 지속적인 할 일은 MAILBOX가 정본이며 수신/반영 미확인이다.

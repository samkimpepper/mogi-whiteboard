## 기존 Orca 기능 확인 — 읽기 전용

`orca-cli`와 `orchestration` 스킬의 로컬 discovery stub 및 설치된 `orca` 실행 파일의 version-matched guide를 읽었다. 환경의 ORCA_CLI_COMMAND·ORCA_DEV_REPO_ROOT가 없어 이 세션에서는 `orca`를 사용했다. `skills get`, messaging-and-gates reference와 명령 help만 읽었으며 Run·Task·Dispatch·새 agent를 만들거나 실제 메시지를 전송하지 않았다.

- Orca에는 기존 terminal send, orchestration send/reply/inbox/check 기능이 있다. 전용 RPC 서버를 새로 만들어야만 전달이 가능한 구조는 아니다.
- orchestration send의 성공은 durable enqueue이며 wake/nudge는 best-effort attention이다. 수신자가 읽거나 새 turn을 시작했다는 증명이 아니다. 실행 중 기존 두 세션의 실제 지원·호환성은 이번 조사에서 검증하지 않았다.
- terminal send는 살아 있는 터미널에 입력을 보내는 기능이며 input accepted와 turn started를 구분한다. structured task·reply 추적에는 별도 orchestration 계약이 있다. 현재 두 역할을 임의로 supervised worker로 등록해 전체 lifecycle을 도입하지 않는다.
- 부팅 읽기 규칙은 상대 세션이 새로 시작할 때 보완할 수 있지만 실행 중 세션의 알림을 대신하지 못한다. 종료된 상대를 다시 시작할 정책도 별도로 필요하므로 자동 세션 생성까지 이번 제안에 포함시키지 않는다.

현재 권고는 모기가 승인한 내용을 durable하게 남긴 뒤, 기존 Orca 전달 기능으로 상대의 살아 있는 세션에 확인 요청을 보낼 수 있는지 좁게 검증하는 것이다. 가능한 경우 모기가 매번 읽으라고 시키는 부담을 줄이고, 파일은 오프라인 때 미수신 내용 보존에 사용한다. ACK·DONE 답장은 전달 확인을 보완하되 알림 자체를 해결한 것으로 표현하지 않는다. 승인된 내용만 보내는 정본과 작성자 보고/독립 확인 구분은 유지한다.

제안 검토와 관찰 기록만 남겼으며 구현·MAILBOX 전달·규칙 정본 변경·커밋·푸시는 하지 않았다.

실험·메시지 전송·자동화 구현은 시작하지 않았다. 이번 발언은 관찰 기록으로만 남겼으며 MAILBOX나 규칙 정본으로 전달하지 않았다.

## 구현 구조 재논의

모기가 에이전트끼리 통신을 어떻게 구현할지 다시 물었다. 이전의 실험 대기 지시는 실제 전송·구현 승인으로 바꾸지 않고 구현안을 설명하는 요청으로 해석했다.

설치된 Orca의 version-matched 가이드·send/check help·status·명령 목록만 다시 읽었다. runtime은 ready이고 terminal prompt delivery 및 orchestration capability가 광고돼 있다. 이것만으로 현재 화이트보드냥·투두냥의 두 세션이 CLI 수신 대상으로 호환됨을 확인한 것은 아니다. 일반 세션을 임의로 supervised Run·Task·Dispatch에 편입하지 않는다.

첫 구현 후보는 승인된 내용의 기존 파일 기록과 한 번의 확인 알림을 연결하는 작은 함수다. 수신 대상은 역할 이름으로 현재 살아 있는 세션을 찾아 명확하게 하나만 선택하고, 호환되는 terminal이면 terminal send로 확인 요청 한 줄을 보낸다. 본문·결과 보존과 완료 판단은 알림 명령에 맡기지 않는다. 현재 두 세션의 실제 주소·지원 여부가 첫 확인 대상이며, 여러 후보·대상 없음·미확인 수신을 성공으로 처리하지 않는다. 재시작 후 runtime handle을 재조회하고, input accepted·turn started·내용 인수·구현 완료를 구분한다. 상대가 종료돼 있으면 파일은 남기고 자동 새 세션 생성은 첫 범위에 넣지 않는다.

결과를 같은 경로로 알려줄 경우 수신자가 결과 근거를 남기고 반대 방향으로 확인 알림을 보낸다. 파일 전체 비우기 규칙을 양방향 파일에 그대로 적용하지 않으며, 결과 답장 추가 시 수신 방향과 소비 단위를 따로 정해야 한다. 작성자 완료 요약은 검증할 commit·범위의 안내이며 독립 diff 확인을 대체하지 않는다. 실제 코드 작성·메시지 전송·새 세션 생성·MAILBOX 변경은 수행하지 않았다.

## 수신 세션 발견과 역할 등록

모기는 새 세션에서 terminal ID가 바뀌므로 서로 세션을 찾고 현재 주소를 알리는 과정이 먼저 필요하다고 지적했다. 역할 이름·작업공간은 지속적인 식별자로 두고 실제 수신 주소는 세션 시작 시 등록하고 전송 때 현재 Orca 목록과 대조하는 구조가 필요하다는 데 동의했다.

제안 단계의 resolveRecipient(role)는 역할 등록에서 작업공간과 수신 세션 정보를 찾고, 현재 runtime의 세션·terminal 목록에서 그 주소와 실제 대상·지원 경로를 검증한다. 예전 handle을 고정하거나 같은 레포의 가장 최근 세션·제목만으로 발송 대상을 정하지 않는다. 같은 작업공간에 여러 세션이 있을 수 있으므로 현재 역할을 맡은 세션의 명시적 등록이 필요하다. 재시작·주소 변경 시 해당 역할의 등록을 갱신한다. 찾지 못하거나 여러 후보가 있으면 미전송으로 남기며, 주소 부재를 기존 세션 종료의 증명으로 삼지 않는다.

등록의 저장 위치·형식 및 현재 두 세션의 native/terminal 주소 호환성은 아직 결정·검증하지 않았다. 역할 등록도 수신자가 읽었다는 ACK나 구현 완료 보고를 대체하지 않는다. 실제 등록·전송·통신 실험은 시작하지 않았다.

역할별 `whiteboard.json`·`todo.json`을 나누어 각 역할은 자기 등록만 쓰고 상대 등록은 읽는다. runtime·현재 주소는 일시적인 상태이므로 폴더는 Git에서 제외하고, 공통 경로와 읽기·등록 규칙만 각 역할의 진입 문서에 남기는 안이다. 이 저장소 HANDOFF와 투두냥의 진입 문서에 안내가 필요하지만 원본 mogi-productivity 문서는 기존 역할 경계를 따라 투두냥이 맡는다. 경로가 있다고 자동 발견되는 것이 아니라 세션 시작 규칙에서 연결해야 한다.

제안만 설명했으며 폴더·등록 파일·ignore 규칙을 만들거나 원본 문서·MAILBOX를 변경하지 않았다. 통신 실험은 여전히 대기 중이다.

모기는 화이트보드냥이 MAILBOX에 데이터를 채워 넣으면 곧바로 상대에게 통신해 확인을 요청하는 방식이 나은지 물었다. 승인된 전달사항을 저장하는 주체가 저장 성공 직후 알림을 한 번 보내는 흐름이 현재 불편을 직접 줄인다고 판단했다. 파일 감시나 상시 폴링 없이 작성 흐름에 연결하는 후보이며 실제 실행 승인은 아니다.

순서는 기존 미수신 내용을 보존해 승인된 내용을 저장하고 성공을 확인한 뒤, 현재 수신 세션을 찾아 확인 알림을 보내는 것이다. 관찰 일지·자체 발견·Cubic 지적을 썼다는 이유만으로 발동하지 않으며 MAILBOX 전달 범위 정본을 유지한다. 저장 실패 시 알림을 보내지 않고, 저장 성공 뒤 전송 실패·대상 불명확이면 전달사항은 남기고 미전송·수신 미확인 상태를 구분한다. 침묵이나 input accepted만으로 읽음·인수·완료라고 판정하거나 무조건 재전송하지 않는다. 이미 처리 중인 상대를 강제로 중단하는 동작은 첫 알림에 포함하지 않는다.

ACK 자체를 다시 알림하는 왕복 루프는 만들지 않는다. 결과 보고 후 반대 방향의 확인 알림은 별도 트리거로 논의할 수 있지만 이번 질문으로 자동 도입하지 않았다. 실제 MAILBOX 작성·등록·전송·자동화는 수행하지 않았다.

이후 모기가 실험 시작과 현재 terminal 주소 등록을 요청해, 역할 등록과 한 번의 등록 확인 요청을 실행했다. 앞의 미실행·대기 상태는 당시 기록이며 [등록 실험 결과](2026-10-02-agent-registration.md)가 후속 상태다. MAILBOX 자동 알림 전체 도입은 아직 하지 않았다.

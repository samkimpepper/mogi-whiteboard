2026-10-06 모기가 논의한 계획을 기록해 달라고 요청했다. **합의한 설계 기록이며 아직 구현·설치하지 않았다.** 부팅 지침 변경, 주소 파일 생성, 기존 등록 스크립트 교체, 원본 mogi-productivity 수정은 이번 요청에 포함하지 않는다. 후속 구현의 실행 지시·전달은 기존 MAILBOX 규칙을 따른다.

## 역할과 주소

역할은 레포의 시작 지침으로 정하고, Run ID는 그 역할을 맡은 현재 세션의 우편함 주소로 사용한다. 모기가 Codex를 켤 때마다 역할이나 Run ID를 수동으로 전달하지 않아도 되게 하는 것이 목적이다.

| 역할 | 등록 가능한 기본 조건 | 자기 주소 파일 |
|---|---|---|
| 투두냥 | 이 Mac의 로컬 Orca에서 실행한 Codex 최상위 대화, Orca 작업공간이 `/Users/leechaerim/orca/mogi-productivity`의 primary/main 작업공간 | `mogi-productivity/.local/agent-address.json` |
| 화이트보드냥 | 이 Mac의 로컬 Orca에서 실행한 Codex 최상위 대화, Orca 작업공간이 `/Users/leechaerim/orca/mogi-whiteboard`의 primary/main 작업공간 | `mogi-whiteboard/.local/agent-address.json` |

서브에이전트·feature worktree 작업자는 자동 등록 대상에서 제외한다. 작업 중 shell cwd가 feature checkout으로 이동한 사실만으로 담당 역할을 바꾸지 않는다. 터미널 제목이나 최근 대화 내용만 보고 상대를 역할 담당자로 등록하지 않는다. 시작 지침과 이 조건은 협력하는 로컬 세션의 식별 규칙이지 보안 인증 수단은 아니다.

## 기록할 정보

각 주소 파일은 Git에서 제외하고 해당 역할이 자기 것만 쓴다. 상대 파일은 읽기만 한다.

- 역할, 스키마 버전, 정규화한 레포/Orca 작업공간 경로
- Codex 대화 세션 ID: 같은 대화의 재개인지 새 대화인지 구분
- Orca Run ID: 메시지 수신 주소
- 현재 터미널 handle·incarnation ID·runtime ID·execution host: 연결이 바뀌었는지 대조
- 등록 세대 번호와 등록/갱신 시각

실제 필드명·Codex 세션 ID 조회 방법은 구현 시 현재 Orca/Codex가 제공하는 근거를 확인해 정한다. 식별 정보를 확실히 얻지 못하면 추정값으로 등록하지 않는다.

## 부팅 시 자기 등록

1. 자기 역할의 조건과 현재 세션 식별 정보를 확인한다.
2. 자기 주소 파일의 짧은 등록 잠금을 잡고 기존 기록·현재 Orca 상태를 확인한다. 두 세션이 동시에 빈 파일을 보고 둘 다 담당자가 되는 일을 막는다.
3. 아래 동시 세션 규칙으로 등록 권한을 판단한 뒤 자기 Run binding을 확인한다. 동일 담당자의 유효한 기존 Run은 유지하고, 필요한 경우에만 새 Run을 만든다.
4. 확인한 주소를 원자적으로 기록하고 잠금을 푼다. 재등록은 같은 세션에 대해 멱등이어야 한다. 다른 역할의 Run을 대신 만들거나 binding을 바꾸지 않는다.

새 담당자가 된 경우에는 등록 세대 번호를 올린다. 같은 세션의 정상 재개·주소 정보 갱신만으로 새 담당자라고 간주하지 않는다. Run 생성과 파일 기록 사이 실패의 복구 방식은 구현 시 정하며, 결과가 불명확하면 새 Run을 반복 생성하지 않고 현재 상태부터 확인한다.

## 동시에 켰을 때

**실행 중인 Codex는 여러 개일 수 있지만 역할별 대표 등록은 하나다.**

| 상황 | 처리 |
|---|---|
| 같은 Codex 대화를 두 창에서 열음 | 같은 담당자로 취급하고 기존 Run·대표 연결을 유지한다. 새 창이 주소를 서로 덮어쓰거나 Run을 추가 생성하지 않는다. |
| 다른 Codex 대화를 같은 레포에서 열음 | 기존 담당자의 연결이 확인되면 유지한다. 새 세션은 담당 역할을 자동으로 가져가지 않는다. |
| 기존 담당자의 종료가 확실함 | 잠금 안에서 다시 확인하고 새 세션이 새 세대로 등록할 수 있다. |
| 기존 담당자의 연결 상태가 불명확함 | 자동 교체·덮어쓰기를 하지 않고 모기에게 확인한다. |
| 모기가 새 세션으로 교체하라고 명시함 | 새 담당자를 등록하며 세대 번호를 올린다. 이전 담당자는 다음 송수신 전 세대 불일치를 확인하고 역할 통신을 중단한다. |

응답 지연, idle, 일시 연결 끊김, 목록에서 안 보임만으로 종료를 확정하지 않는다. 같은 대화가 여러 창에 연결될 때 대표 연결을 유지·이전하는 정확한 방법과 확실한 종료의 판정 근거는 구현 전 실제 Orca 동작으로 확인한다.

## 송수신

보내기 전에 자기 등록 세대·대표 연결과 상대 파일의 Run/세션/터미널 연결을 현재 Orca 정보에 대조한다. 낡았거나 불명확한 주소로 추측 전송하지 않는다. 받는 쪽도 현재 대표인지 확인한 뒤 역할 메시지를 처리한다. 세대 검사는 오래된 담당자의 이후 송수신을 막는 협력 규칙이며 이미 진행 중인 일을 취소하는 기능은 아니다.

내용은 MAILBOX에 두고 Orca는 필요한 알림·답장에 사용한다. 메시지 저장, 실제 수신, 업무 인수, 처리 완료를 구분하고 실제 읽고 처리한 delivery만 ACK한다. 대화에 들어오는 Orca 알림 문장은 모기가 직접 작성한 업무 지시로 간주하지 않고 check로 발신자와 본문을 확인한다.

부팅 때마다 자동 인사 메시지를 보내지 않는다. 새 연결의 첫 실제 전달에서는 발신자와 수신을 확인하는 답장을 사용한다. 알림이 입력을 끊는 문제는 별도이며, 주소 등록으로 해결됐다고 주장하지 않는다. 상시 polling·자동 MAILBOX 알림 훅은 이 계획에 포함하지 않는다.

## 검증할 동작과 범위

구현 검증에서는 동시 최초 등록의 대표 한 명, 동일 세션 재개의 Run 유지, 다른 살아 있는 세션의 덮어쓰기 거절, 불명확한 종료의 교체 보류, 명시적 교체 후 이전 세대의 통신 거절, 오래된 상대 주소의 전송 중단을 확인한다. 같은 세션의 두 창에서 중복 소비가 없는지도 실제 지원 범위와 함께 확인한다.

등록 잠금은 대표 주소를 정하는 동안만 사용한다. **공유 레포의 코드 편집·이미 시작한 작업까지 잠그는 장치가 아니다.** Task/Dispatch 감독, 에이전트 생성, 전체 하네스 도입으로 확대하지 않는다.

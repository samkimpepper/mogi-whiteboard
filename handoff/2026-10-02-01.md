## 마지막 질문과 조사 결론

모기가 투두냥 화면에서 우리 메시지가 사람 프롬프트처럼 보여 모기와 화이트보드냥을 구분하기 어렵다고 지적했다. terminal send는 사용자 입력 칸으로 들어간다. 발신자 prefix는 협력적 구분 안내일 뿐 UI의 실제 발신자 역할이나 인증을 바꾸지 않는다. prefix·수신 규칙은 논의했지만 아직 적용·재실험하지 않았다.

모기 요청으로 `/Users/leechaerim/orca/mogui-ADE-orchestrator` checkout `962e7c1`을 읽기 전용으로 조사했다. 실제 작업 배정 코드는 `orchestration dispatch --inject`, 상태·완료 수신은 `orchestration send/check`와 worker_done 경로다. spawn-test는 첫 지시에는 terminal send, 결과 메시지에는 orchestration send를 함께 쓴다. peer/master 간 주소는 순간적인 handle 대신 standing Run에 연결하고, ACK 누락으로 queue가 막힌 사고도 기록돼 있다. turn 시작 hook은 완전히 쉬는 세션을 자동으로 깨우지 못한다.

**orchestration send/check/reply는 Orca 기본 기능**이다. 하네스 도입 없이 쓸 수 있지만 현재 두 세션에 맞는 Run 주소·binding·수신 동작을 확인해야 한다. 하네스 전체의 규칙·감독 체계를 우리 역할에 자동 적용하지 않는다. 현재 Orca의 version-matched 가이드를 우선하며 오래된 하네스 wrapper를 그대로 실행하지 않는다. 현재 두 냥이의 Run 생성·binding·별도 우편함 메시지 전송이나 실제 UI 발신자 표시 검증은 하지 않았다.

조사 근거와 파일·줄 위치는 [하네스 통신 조사](../sessions/2026-10-02-orchestrator-communication.md), 제안 경과는 [MAILBOX 제안 검토](../sessions/2026-10-02-mailbox-proposal-review.md). `orca-cli`·`orchestration` 스킬을 사용했고 선택한 실행 파일은 `orca`였다. 현재 guide를 읽고 권한/Dispatch 맥락을 확인해 진행한다. 별도 Run 없이 일반 세션을 임의로 supervised worker로 취급하지 않는다.
